# Phase 1: Фундамент и аутентификация - Context

**Gathered:** 2026-07-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Заложить каркас приложения и границу изоляции данных по пользователю, а также полный цикл аутентификации: регистрация → вход → выход → попадание в свой личный (пустой) список.

**В охвате:**
- Скаффолд Next.js 16 (App Router) + TypeScript + Tailwind v4, подключение Postgres через Drizzle, конфигурация Better Auth (email/password).
- Экраны: регистрация, вход, пустой список (защищённый), минимальная шапка приложения.
- Слой данных, ограниченный текущим `userId` (граница изоляции), с тестом изоляции на двух пользователях.

**Вне охвата (другие фазы):**
- Форма добавления покупки и движок подсчёта очков — Фаза 2.
- Любые CRUD-операции по покупкам, сортировки, фильтры, архив — Фазы 3–4.
- Верификация email, 2FA, magic links, восстановление пароля — не в v1.

</domain>

<decisions>
## Implementation Decisions

### Регистрация
- **D-01:** Поля регистрации — только `email` + `password`. Отображаемое имя не запрашиваем; в шапке показываем email. — **Reversibility:** costly — добавление обязательного `name` позже потребует миграции схемы Better Auth и обновления формы/шапки.
- **D-02:** Верификация email в v1 не требуется — после регистрации пользователь сразу авторизован (без email-провайдера/SMTP).
- **D-03:** Минимальная длина пароля — 8 символов (дефолт Better Auth).
- **D-04:** После успешной регистрации выполняется автоматический вход (создаётся сессия) и редирект на личный список — без промежуточного экрана «войдите вручную».

### Точка входа и навигация
- **D-05:** Корневой URL `/` для неавторизованного посетителя — редирект на `/login`. Отдельной лендинг-страницы нет; приложение = личный список за авторизацией. — **Reversibility:** reversible.
- **D-06:** Пустой список в Фазе 1 — заглушка (empty state) с подсказкой вроде «Список пуст — скоро можно будет добавить покупки». Реальная форма/кнопка добавления появится в Фазе 2; в Фазе 1 её нет.
- **D-07:** При отсутствии или истечении сессии на защищённой странице — редирект на `/login` (без промежуточного сообщения).

### Оболочка и выход
- **D-08:** В Фазе 1 закладывается минимальная общая шапка (layout): название приложения + email пользователя + кнопка «Выйти». Служит каркасом для будущих экранов.
- **D-09:** После выхода пользователь попадает на `/login`; сессия очищается.

### Сессия
- **D-10:** Чекбокса «Запомнить меня» нет — всегда длинная persistent-сессия (сохраняется между перезагрузками страницы, покрывает AUTH-02).
- **D-11:** Срок жизни сессии — 30 дней. Требует явной настройки `session.expiresIn = 60*60*24*30` — дефолт Better Auth равен 7 дням, а не 30 (уточнено в RESEARCH.md).

### Хеширование и слой данных (resolved 2026-07-26)
- **D-12:** Хеширование паролей — **Argon2id** (в соответствии с `.claude/CLAUDE.md`), через `@node-rs/argon2` + кастомные `password.hash`/`password.verify` в конфиге Better Auth (переопределяет дефолтный `scrypt` Better Auth, уточнённый в RESEARCH.md). — **Reversibility:** costly — смена алгоритма хеширования позже потребует ре-хеширования существующих паролей (миграция или re-hash-on-login).
- **D-13:** Фаза 1 создаёт минимальную таблицу `items` + read-only слой доступа к данным, ограниченный `userId` (`getCurrentUser()` из серверной сессии → `findItemsForUser`), **без** формы/записи/UI (соблюдает пустой стейт D-06). Это делает тест изоляции на двух пользователях (критерий успеха №4) настоящим — с посевом строк и проверкой, что пользователь A не видит данные пользователя B — и служит фундаментом для CRUD покупок в Фазе 2. — **Reversibility:** reversible.

### Claude's Discretion
- Язык интерфейса — русский (все пользовательские тексты/копирайт на русском; код, идентификаторы, пути — на английском).
- Тексты ошибок аутентификации: при входе — обобщённое «Неверный email или пароль» (не раскрывать, существует ли аккаунт); при регистрации — явное «Этот email уже занят». Прочие формулировки ошибок валидации — на усмотрение планировщика/исполнителя, единый тон.
- Точная структура маршрутов (`/login`, `/register`/`/signup`, `/list` или `/`) — на усмотрение планировщика, при условии соблюдения решений D-05…D-09.
- Механизм защиты маршрутов (middleware vs проверка сессии в серверном компоненте/layout) — на усмотрение планировщика. Уточнение RESEARCH.md: в Next 16 `middleware.ts` переименован в `proxy.ts`, а проверка cookie в proxy — оптимистичная и небезопасная; рекомендуется серверная проверка `getSession()` в layout группы `(app)`.
- Стратегия тестовой БД — выделенная локальная Postgres-база для тестов (рекомендация RESEARCH.md) вместо Testcontainers для этого MVP.

</decisions>

## Existing Code Insights

### Reusable Assets
- Пусто — greenfield. Кода приложения ещё нет (нет `package.json`), только `.planning/` и `SUMMARY.md`.

### Established Patterns
- Паттернов пока нет. Фаза 1 задаёт их: структура App Router, слой данных Drizzle с обязательным scoping по `userId`, TDD-обвязка (Vitest + Playwright).

### Integration Points
- Better Auth монтируется одним catch-all роутом Next.js (`toNextJsHandler`).
- Таблицы Better Auth (users/sessions/accounts/verification) живут в том же Postgres через первопартийный Drizzle-адаптер; миграции — `drizzle-kit generate`/`migrate`.
- Граница изоляции: единая точка доступа к данным, принимающая `userId` из серверной сессии — фундамент для CRUD покупок в Фазах 2–5.

<specifics>
## Specific Ideas

- Приложение задумано как «список за авторизацией» без публичного лендинга — вход/регистрация являются входной точкой.
- Семейный/личный сценарий использования → приоритет удобства над строгой безопасностью (мягкие требования к паролю, длинная сессия, без верификации email).
- Изоляция данных должна быть проверяема автотестом на двух пользователях (критерий успеха №4 фазы) — это ключевой якорь для Playwright-теста.

</specifics>

<deferred>
## Deferred Ideas

- Верификация email / восстановление пароля / 2FA / magic links — плагины Better Auth, кандидаты для будущих фаз (не v1).
- Рейт-лимит попыток входа — обсуждалось как возможная развилка, в Фазу 1 не берём (Better Auth поддерживает плагином позже при необходимости).
- Отображаемое имя пользователя и приветствие по имени — если понадобится, отдельная небольшая доработка (см. D-01, потребует миграции).

</deferred>
