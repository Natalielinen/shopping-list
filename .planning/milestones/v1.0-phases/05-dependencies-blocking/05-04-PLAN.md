## Phase Goal (MVP-срез)

**Как** авторизованный пользователь, **я хочу**, чтобы систему нельзя было заставить отметить заблокированную покупку купленной (даже в обход недоступного чекбокса), **чтобы** порядок «сначала зависимость, потом зависимая» соблюдался надёжно, а не только визуально.

> История выведена дословно из ROADMAP `**Goal:**` Фазы 5 + success criteria SC-2.

**Срез плана 05-04 (расширение поверх верифицированного tracer'а):** серверный guard defense-in-depth в `setItemPurchased` (D-03) — авторитетный backstop к `disabled`-чекбоксу из плана 05-03 — плюс проброс серверного текста ошибки в тост и человеко-проверка визуальных бэкстопов (усечение длинных названий на 375px, LIST-08 mobile-first).

<objective>
Замкнуть контур блокировки со стороны сервера и подтвердить визуал:
1. Добавить в `setItemPurchased` (Server Action Фазы 4) guard: при отметке «куплено» заблокированной покупки вернуть `{ ok:false, error: BLOCKED_ERROR }` через существующий `findItemForUser` + чистый `isBlocked` (план 05-01). Снятие «куплено» — всегда без guard.
2. Пробросить серверный текст ошибки в `PurchaseCheckbox` (`toast.error(res.error)`), чтобы обойдённый `disabled`-UI объяснил причину (S3 error).
3. Доказать guard action-уровневым интеграционным тестом на реальной PG.
4. Человеко-проверить визуальные бэкстопы (усечение длинного названия зависимости и длинной опции Select на 375px), которые нельзя проверить автоматически.

Purpose: `disabled`-чекбокс — клиентская подсказка, не защита (never-trust-client). Guard делает блокировку авторитетной на сервере (D-03), закрывая Tampering-угрозу обхода запроса. Визуальные бэкстопы требуют глаза человека (перенос практики Фаз 3–4 — не фабрикуются).
Output: серверный guard + серверный текст ошибки в тосте + зелёный guard-тест + подтверждённый визуал.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client (запрос «куплено») → Server Action | `disabled`-чекбокс — клиентская подсказка; подделанный/обойдённый запрос пересекает границу и обязан быть отклонён на сервере. |
| Server Action → repo → Postgres | Guard читает покупку и зависимость через userId-scoped findItemForUser; blocked — производное на чтении, не хранится. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-02 | Tampering | Обход disabled-чекбокса подделанным запросом «куплено» (setItemPurchased) | high | mitigate | Серверный guard (D-03): при next и заблокированной покупке → { ok:false, error: BLOCKED_ERROR } ДО записи. Доказывается action-уровневым интеграционным тестом на реальной PG. Defense-in-depth к disabled-UI. |
| T-05-01 | Information Disclosure / Elevation | Чтение зависимости в guard | high | mitigate | Guard использует findItemForUser (userId-scoped) — чужую покупку/зависимость прочитать нельзя (перенос T-3-02); userId только из requireUser(). |
</threat_model>
