## Phase Goal (MVP-срез)

**Как** авторизованный пользователь, **я хочу** сделать одну свою покупку зависящей от другой и видеть её заблокированной, пока зависимость не куплена, **чтобы** покупать вещи в правильном порядке.

> История выведена дословно из ROADMAP `**Goal:**` Фазы 5 + success criteria.

**Срез плана 05-02 (модель данных + миграция):** заложить единственный необратимый шаг фазы — self-referencing FK `depends_on` в `items` через миграцию — плюс контракт валидации (`dependsOn` в Zod) и нормализацию репозитория, чтобы прошивающий tracer (план 05-03) работал поверх уже мигрированной схемы с реальной БД. Содержит [BLOCKING] миграцию (после правок схемы, до верификации) и reversibility-гейт one-way перед ней.

<objective>
Установить схему и контракт данных зависимости:
1. Добавить в `items` (schema.ts) nullable self-FK `dependsOn` (`depends_on`) с `AnyPgColumn`-аннотацией (разрыв циклической инференции, Pitfall 1) и `onDelete: "set null"` (D-06).
2. Расширить `itemInputSchema` полем `dependsOn` (optional/nullable, sentinel `"none"`/`""`→null) по образцу хелперов `optionalUrl`/`optionalText`; добавить кейсы в `item.test.ts`.
3. Нормализовать очистку в `updateItemForUser` (`dependsOn: data.dependsOn ?? null`) рядом с link/description/deadline (CR-01 / Pitfall 4).
4. Расширить `seedItem` опциональным `dependsOn` для графовых сидов интеграционных тестов.
5. [BLOCKING] Сгенерировать и применить миграцию (`drizzle-kit generate` → `0003_*.sql` → `drizzle-kit migrate`), закоммитить SQL + meta.
6. Доказать поведение FK интеграционными тестами на реальной PG: onDelete set null, persist `dependsOn`, очистка → NULL.

Purpose: миграция — единственный one-way шаг фазы; она обязана лечь ДО tracer'а, иначе build/типы пройдут ложно-зелёно (типы идут из schema.ts, а не из живой БД — schema-gate). Reversibility-гейт даёт человеку подтвердить дверь перед её проходом.
Output: мигрированная схема с self-FK + расширенный Zod/repo + зелёные интеграционные тесты FK.
</objective>

<assumption_delta_decision>
Первичное существительное: `dependency` (зависимость покупки).
Решение: **no-change** — единичная `dependsOn` (nullable self-FK) остаётся выбранной v1-идентичностью (D-01). Множественные зависимости (join-таблица many-to-many) явно отложены в v2 (CONTEXT §Deferred). Это не singular→plural переход: модель сознательно единична; join-таблица — признанный будущий promote-path, не добавляется alongside сейчас.
Рационал: одна строка ссылается максимум на одну зависимость; блокировка прямая (D-02). Расширение до many легко достигается новой таблицей без ломки существующего FK.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Server Action → repo → Postgres | `dependsOn` — недоверенный пользовательский ввод, ссылающийся на другой ряд `items`. Пересекает границу через Zod-валидацию (форма) и параметризованный Drizzle-запрос (repo). |
| Postgres FK-констрейнт | FK гарантирует ссылочную целостность к таблице `items`, но НЕ владельца строки. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-05-05 | Tampering | dependsOn → items (INSERT/UPDATE) | medium | mitigate | Параметризованные Drizzle `.values()`/`.set()`/`eq` — нет SQL-инъекции через dependsOn (перенос T-2-10). Zod приводит dependsOn к строке/null. |
| T-05-01 | Information Disclosure / Elevation | FK items.depends_on (целостность без владельца) | high | mitigate | FK НЕ проверяет владельца — ownership-проверка (`candidate ∈ findItemsForUser(userId)`) выполняется в Server Action (план 05-03).
