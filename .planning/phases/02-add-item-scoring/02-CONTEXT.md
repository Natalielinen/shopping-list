# Phase 2: Добавление покупок с автоматическим приоритетом - Context

**Gathered:** 2026-08-01
**Status:** Ready for planning

<domain>
## Phase Boundary

Авторизованный пользователь может добавить покупку через форму и сразу видит её автоматически рассчитанный приоритет (`total`) с разбивкой по полям, объясняющей оценку.

**В охвате:**
- Форма добавления покупки: обязательные `title` + выпадающие списки `category` / `urgency` / `need` / `benefit`; необязательные `link`, `description`, `price`, `deadline`, `doubts`, `isCredit` (+ условное `monthlyPayment`).
- Чистый модуль подсчёта очков (pure functions): очки по `category` / `urgency` / `need` / `benefit`, `doubts` (0/−1/−3), штраф за кредит (−2), `deadlinePoints` (формула с внедряемыми «часами»), `total` = сумма — считается **на чтении** и отражает сегодняшнюю дату (SCORE-05).
- Расширение таблицы `items` полями покупки + запись (insert) через слой данных со scoping по `userId`.
- Badge приоритета (LIST-06) и разбивка очков по полям (LIST-07) на карточке покупки.
- Отображение списка покупок с badge, отсортированного по приоритету.

**Вне охвата (другие фазы):**
- Редактирование и удаление покупок с пересчётом — Фаза 3 (ITEM-07, ITEM-08).
- Переключатели сортировки (по добавлению/алфавиту), фильтр «показывать купленные», отметка «куплено» и архив — Фаза 4 (LIST-01…05, LIST-08).
- Зависимости (`depends`) и блокировка — Фаза 5 (ITEM-06, DEP-01, DEP-02).

</domain>

<decisions>
## Implementation Decisions

### Шкалы очков (открытые пункты SUMMARY закрыты)
- **D-01:** `DoubtsType` — три пункта: «Уверен(а)» (0, по умолчанию), «Сомневаюсь» (−1), «Сильно сомневаюсь» (−3). Очки зафиксированы roadmap (SCORE-04); закрыты только названия/тон. — **Reversibility:** reversible.
- **D-02:** `BenefitType` — зафиксирован набор из 5 пунктов ровно как в `SUMMARY.md`: «Экономит время/деньги/силы» +1, «Расходует время/деньги/силы» −1, «Никаких выгод» 0, «Приносит доход» +2, «Тратит больше, чем стоит» −2. Поле обязательное (критерий успеха №1). Снимает пометку «(обсудить)» из SUMMARY.
- **D-03:** `UrgencyType` «Жизненно важно» = **12 очков** (в SUMMARY значение отсутствовало). Становится самым высоким уровнем срочности — выше «экстра срочности» (10). Остальные пункты urgency — по SUMMARY (экстра 10, очень срочно 4, срочно 3, не очень срочно 2, не срочно 1).
- **D-04:** `deadlinePoints` — без дедлайна = 0; иначе `clamp(28 − дни_до_дедлайна, −100, 100)`. Крайние случаи: дедлайн сегодня (0 дней) = +28; **любой просроченный дедлайн (дни < 0) = +100** (фиксированный максимум, а не растущее по формуле значение) — просрочка трактуется как самый срочный случай. — **Reversibility:** reversible (чистая функция, покрыта юнит-тестами).
- **D-05:** `total` = простая сумма всех очковых полей (category + urgency + need + benefit + deadlinePoints + doubts − 2·isCredit). Считается **на чтении** с внедряемой «текущей датой» (SCORE-01, SCORE-05); не «замораживается» при создании. `category` / `urgency` (кроме «Жизненно важно») / `need` — по фиксированным шкалам SUMMARY (SCORE-06).

### Форма добавления
- **D-06:** Форма живёт на **отдельной странице** (напр. `/list/new`), полноэкранной — удобнее для многополевой формы на мобильном, чисто работает с RSC + Server Action, не требует нового shadcn-компонента (Dialog не установлен). — **Reversibility:** reversible.
- **D-07:** **Все поля показываются сразу** (без сворачивания необязательных в отдельную секцию). `monthlyPayment` появляется условно при `isCredit = true` (ITEM-04).
- **D-08:** Вход в форму — **кнопка «Добавить» в шапке приложения** (переиспользует `AppHeader.tsx`) + кнопка в пустом состоянии списка (сейчас там заглушка из Фазы 1, D-06 Фазы 1). — **Reversibility:** reversible.
- **D-09:** После успешного сохранения — **редирект на список**, где сразу видна новая покупка с badge. — **Reversibility:** reversible.

### Badge и разбивка приоритета
- **D-10:** Badge показывает **число `total` + цветовой уровень** (высокий/средний/низкий по порогам). Доступность: уровень кодируется не только цветом, но и текстом/иконкой (LIST-06). Конкретные пороги и палитра — на усмотрение UI-фазы/планировщика.
- **D-11:** Разбивка очков по полям (LIST-07) **раскрывается по тапу** на карточке/badge (компактно на мобильном), а не показана постоянно.

### Список в Фазе 2
- **D-12:** Список отображается **сразу отсортированным по убыванию `total`** — core value виден уже в этой фазе. Переключатели сортировки, фильтры, архив и «куплено» — Фаза 4. Детерминированный tiebreaker при равном приоритете формализуется в Фазе 4; в Фазе 2 достаточно стабильного порядка (напр. по `createdAt`).

### Claude's Discretion
- Форматы ввода `price` (валюта/десятичные) и `deadline` (date input / date picker) — на усмотрение планировщика.
- Тайминг валидации (на сабмите vs live) и точные тексты ошибок — на усмотрение планировщика; единый тон, интерфейс на русском (перенос из Фазы 1).
- Точный маршрут формы (`/list/new` или иной) — на усмотрение планировщика при соблюдении D-06…D-09.
- Механика data flow (Server Action + `useOptimistic` / `useActionState`) — на усмотрение планировщика согласно `.claude/CLAUDE.md`.
- Пороги уровней badge и палитра (D-10) — на усмотрение UI-фазы.

</decisions>

## Existing Code Insights

### Reusable Assets
- `src/server/repos/items.ts` (`findItemsForUser`) — слой доступа к покупкам; сюда добавляется `insert` со scoping по `userId` (шов изоляции AUTH-04).

- `src/lib/validation/auth.ts` + тесты — паттерн Zod-схем с юнит-тестами (TDD); движок подсчёта и item-схема следуют тому же паттерну.
- `src/components/ui/*` — shadcn: `button`, `card`, `form`, `input`, `label`, `alert`. **Select для выпадающих списков НЕ установлен** — потребуется добавить (shadcn Select).
- `src/components/app/AppHeader.tsx` — сюда добавляется кнопка «Добавить» (D-08).
- `src/app/(app)/list/page.tsx` — экран списка (сейчас пустое состояние из Фазы 1); расширяется карточками покупок с badge.

### Established Patterns
- Слой данных: `userId` обязателен в сигнатуре и попадает в каждый WHERE (изоляцию нельзя забыть). Запись — всегда `and(eq(id), eq(userId))`.
- Zod — единый источник валидации формы (клиент) и Server Action (сервер), тип выводится из схемы.
- TDD: чистые функции (движок подсчёта, `deadlinePoints`) — юнит-тесты первыми; Server Actions как обычные функции; async Server Components — Playwright.
- Интерфейс на русском; код/идентификаторы/пути — на английском.

### Integration Points
- Новая форма → Server Action (валидация Zod) → `insert` в `items.ts` со scoping по `userId` → редирект на список (D-09).
- Движок подсчёта — чистый модуль, принимающий поля покупки + «текущую дату»; вызывается на чтении списка для `total` и разбивки (SCORE-05).
- Расширение схемы `items` требует миграции `drizzle-kit generate`/`migrate`.

<specifics>
## Specific Ideas

- Просроченный дедлайн = максимальный приоритет (+100), а не постепенный рост по формуле — сознательный выбор пользователя (D-04): просрочка = самое срочное.
- «Жизненно важно» задумано как вершина шкалы срочности (выше аварийного ремонта) — угроза жизни/здоровью важнее всего (D-03).
- Core value (сортировка по приоритету) должен быть виден сразу в Фазе 2, не откладываясь до Фазы 4 (D-12).
- Форма — полноэкранная и «плоская» (все поля сразу), приоритет простоты над компактностью (D-06, D-07).

</specifics>
