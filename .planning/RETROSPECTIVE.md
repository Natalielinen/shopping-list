# Project Retrospective

*Живой документ, обновляется после каждого milestone. Уроки переносятся вперёд в планирование следующих версий.*

## Milestone: v1.0 — MVP

**Shipped:** 2026-10-03
**Phases:** 5 | **Plans:** 20 | **Tasks:** 44

### What Was Built
- Мультипользовательская аутентификация (Better Auth, Argon2id, 30-дневные DB-сессии) с изоляцией данных по `userId` на каждом шве данных, доказанной двухпользовательским тестом (AUTH-01..04).
- Добавление покупок с автоматическим приоритетом: чистый детерминированный движок scoring (category/urgency/need/benefit + deadline + doubts + credit, `now` внедряется, total на чтении), единый Zod-контракт клиент+сервер, badge + раскрываемая разбивка очков (ITEM-01..05, SCORE-01..06, LIST-06/07).
- Полный CRUD покупок: редактирование и удаление с подтверждением (AlertDialog), пересчёт приоритета на чтении, изоляция по `userId` (ITEM-07, ITEM-08).
- Mobile-first список: 3 режима сортировки (приоритет/дата/алфавит с детерминированными tiebreakers), фильтр и обратимый архив «куплено» с undo-тостом (LIST-01..05, LIST-08).
- Зависимости и блокировка: self-referencing FK `depends_on` (ON DELETE SET NULL), серверный guard (defense-in-depth), защита от циклов (visited-set), авто-разблокировка, визуальное отличие заблокированных (ITEM-06, DEP-01, DEP-02).

### What Worked
- **Tracer-first + MVP вертикальные срезы:** каждая фаза вела сквозным end-to-end срезом (форма → Server Action → БД → RSC → UI), доказанным Playwright, прежде чем расширяться. Это держало интеграционные риски видимыми с первого шага.
- **TDD на чистых функциях:** scoring, sort, cycle/blocked — чистые детерминированные модули с юнит-тестами RED→GREEN. Логика приоритета и графа зависимостей закрыта тестами без хрупкости.
- **Изоляция по `userId` в слое данных, а не в UI:** единый шов (`findItemsForUser`/`findItemForUser`) переиспользовался для чтения, проверки владения и guard'ов — IDOR-риск (self-FK ≠ владение) закрыт в одном месте.
- **Миграции generate+migrate в git:** детерминированные SQL-миграции (0001–0003) checked-in; схема — источник типов.

### What Was Inefficient
- **Worktree-режим исполнителей несовместим с проектом:** фазы исполнялись последовательно на основном дереве (`use_worktrees=false`), потому что worktree лишён `node_modules` и untracked `.env.local`/`CLAUDE.md` и ломает тесты. Зафиксировано в конфиге на Фазе 5.
- **Ложная тревога на человеко-проверке Фазы 5:** случайный тап по кнопке «Добавить» принят за баг отметки «куплено»; потребовался repro через Playwright, чтобы подтвердить корректность. Урок: при визуальной проверке фиксировать адресную строку.
- **Дублирование security-инварианта:** проверка владения+цикла скопирована в create/edit Server Actions (найдено code review, вынесено в задачу).

### Patterns Established
- Граница RSC→client — только примитивы (числа/null/boolean), никаких `Date`; производные состояния (приоритет, блокировка, архив) считаются на чтении.
- Server Actions возвращают `{ ok } | { ok: false; error }`; навигация и ресинк — на клиенте (`router.refresh`), без `redirect()` внутри action.
- Деньги — integer-копейки, перевод один раз на сервере.
- Избыточное кодирование статуса (не только цветом): badge/замок/зачёркивание + текст.

### Key Lessons
1. Вертикальный tracer в начале каждой фазы ловит интеграционные проблемы раньше, чем горизонтальные слои.
2. Для этого репозитория исполнители GSD должны идти последовательно на основном дереве — worktree ломает обязательные тесты (persisted в `.planning/config.json`).
3. Внешний ключ гарантирует целостность, но НЕ владение — проверку владельца писать в Server Action/репозитории явно.

### Cost Observations
- Model mix: преимущественно opus (оркестрация + субагенты planner/executor/verifier/reviewer).
- Notable: последовательное исполнение без worktree-параллелизма приемлемо — в большинстве фаз одна-две плана на волну, параллелизм дал бы мало.
